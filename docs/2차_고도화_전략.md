## ⚠️ Phase 1 기술 부채 및 위험요소

### 1. 아키텍처 관련 (Critical 🔴)

#### 1-1. Gemini API 높은 의존성
- **문제**: 마켓 클로징, 수급 요약, 일운세 생성이 모두 Gemini에 의존
  - `market_closing_gemini_service.py` (25KB)
  - `supply_summary_gemini_service.py` (11KB)
  - `daily_fortune_gemini_service.py` (8KB)
- **위험**: API 키 만료, 요청 제한 초과, 응답 파싱 실패 시 서비스 장애
- **개선안**:
  - ✅ Fallback 메커니즘 구현 (기본값 반환)
  - ✅ 캐싱 레이어 추가 (Redis)
  - ✅ 로컬 LLM (Ollama) 옵션 제공

#### 1-2. 마이그레이션 체계 미흡
- **현황**: 17개 마이그레이션이 순차 실행, 실패 시 무시 (main.py line 237-678)
- **위험**: Production 배포 시 부분적 마이그레이션 실패 가능
- **개선안**:
  - ✅ Alembic/Aerich 기반 버전 관리 도입
  - ✅ Dry-run 및 Rollback 메커니즘
  - ✅ 마이그레이션 로깅 강화

#### 1-3. API 인증 정책 불일치
- **현황**: 일부 API는 토큰만, 일부는 API Key만, 일부는 혼합
- **위험**: 보안 관리 난잡, Rate Limiting 부분적 적용
- **개선안**:
  - ✅ 통일된 인증 정책 (토큰 기반, 선택적 API Key)
  - ✅ Global Rate Limiter (slowapi 강화)
  - ✅ 권한 관리 중앙화

---

### 2. 성능 관련 (High ⚠️)

#### 2-1. 스크리닝 병렬 처리 불명확
- **현황**: `jongbe_screening_service.py` 주석 "병렬처리 약 3~5분"
- **문제**: 
  - 4개 스크리닝 × 수백 종목 = 데이터 수집 시간 15분+
  - 장마감 후 피크 시간에 과부하
- **개선안**:
  - ✅ 병렬 처리 검증 및 최적화 (asyncio 강화)
  - ✅ 배치 크기 조정 (100개 단위 청크)
  - ✅ 분산 처리 고려 (Celery)

#### 2-2. 데이터 신선도 vs 성능 트레이드오프
- **현황**: 모든 클라이언트 API 요청이 `cache: no-store` (항상 최신)
- **문제**: DB 쿼리 폭주, 네트워크 대역폭 낭비
- **개선안**:
  - ✅ API별 캐싱 전략 (적응형): 
    - 장중 지수: 1분 캐시
    - 뉴스/분석: 5분 캐시
    - 마스터 데이터: 1시간 캐시
  - ✅ Redis 캐시 층 도입
  - ✅ HTTP 캐시 헤더 활용

#### 2-3. 이미지 최적화 부재
- **현황**: 순수 `<img>` 태그, Next.js Image 미사용
- **문제**: 
  - 대용량 이미지 (뉴스 썸네일 등) 모바일에서 느림
  - WebP/AVIF 지원 없음
- **개선안**:
  - ✅ Next.js Image 도입 (자동 최적화)
  - ✅ 이미지 CDN (Cloudflare, Vercel)
  - ✅ Lazy loading 기본 적용

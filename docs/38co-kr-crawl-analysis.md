## 2. 기술적 분석

### 2.1 인코딩

- 38.co.kr은 **EUC-KR** 계열 인코딩을 사용할 가능성이 높음.
- 크롤링 시 `requests`/`httpx`에서 `response.encoding = 'euc-kr'` 또는 `Content-Type` 확인 후 디코딩 처리 필요.

### 2.2 수집 방식

- **서버 렌더링 HTML**으로 보이므로, 단순 `GET`으로 HTML을 받아 파싱하는 방식이 적합.
- **필요 작업**  
  - HTTP GET → HTML 수신  
  - BeautifulSoup / lxml 등으로 테이블(또는 리스트) 파싱  
  - 기업명, 청약기간, 희망공모가, 주관사, 상세 URL 추출  

### 2.3 URL 패턴

- 목록: `https://www.38.co.kr/html/fund/index.htm?o=k&page=N`  
- 상세: `https://www.38.co.kr/html/fund/?o=v&no={no}&l=&page=1`  
- `no`가 일련번호로 보이므로, 목록 페이지에서 각 행의 상세 링크를 추출해 `no`를 수집하면 됨.

### 2.4 robots.txt

- `https://www.38.co.kr/robots.txt`  
  - `User-agent: *` / `Disallow:` (비어 있음)  
  - **경로 차단은 없음.** (다만 이용약관·저작권은 별도 확인 필요.)

## 4. 구현 시 제안 구조 (참고)

크롤링을 진행한다고 가정할 때:

1. **위치**  
   - Admin(백엔드)에 전용 스크립트 또는 서비스:  
     - 예: `apps/admin/app/services/ipo_schedule_crawler.py`  
   - 주기 실행은 스케줄러(또는 수동 실행)로 제어.

2. **흐름**  
   - 38 목록 페이지(o=k) GET → HTML 파싱  
   - 각 행에서: 기업명, 청약기간(시작/종료), 희망공모가, 주관사, 상세 URL(no) 추출  
   - 필요 시 상세 페이지(o=v&no=…) 추가 수집 (공모가, 확정일 등)  
   - 기존 `Schedule` 모델(또는 전용 IPO 테이블)에 **주관사(underwriter)**, **link_url(38 상세 또는 DART)** 등으로 저장.

3. **저장 전략**  
   - **옵션 A**: 38 데이터를 그대로 “참고용”으로만 쓰고, 실제 서비스 노출은 Admin에서 수동 입력한 일정만 사용.  
   - **옵션 B**: 크롤링 결과를 DB에 반영하되, “출처: 38커뮤니케이션” 표기 및 38 상세 링크를 `link_url`로 저장.

4. **라이브러리**  
   - Python: `httpx`(또는 `requests`) + `beautifulsoup4` / `lxml`  
   - 인코딩: `response.encoding = 'euc-kr'` 또는 `chardet`로 감지 후 디코딩.

## 5. 대안

- **Open DART API**: 공모/증권신고서 정보를 공식 API로 조회 (이미 OPENDART 키 연동 검토됨).  
- **수동 입력**: Admin 일정에서 “주관 증권사”, “DART/증권사 링크”를 직접 입력해 사용 (현재 구현된 방식).  
- **38 크롤링**: 위 리스크를 수용할 수 있을 때만, 이용약관 확인 후 제한적으로 도입.

## 6. 결론

- **가져오는 것 자체는 기술적으로 가능**해 보이며, **HTML 파싱(크롤링)** 방식이 적합합니다.  
- **robots.txt**는 경로 차단이 없으나, **이용약관·저작권** 확인과 **요청 간격·용도 제한**이 선행되어야 합니다.  
- 정식 API가 없는 만큼, 구조 변경 시 유지보수 비용이 들 수 있으므로, **단기 참고용 또는 내부 관리용**으로만 쓰고, 공개 서비스에는 **DART/수동 입력**을 우선하는 편이 안전합니다.
